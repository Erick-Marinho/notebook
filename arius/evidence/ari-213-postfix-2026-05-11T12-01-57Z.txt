# ⚠️ ANOMALIA — Snapshot 11:58:56 com KPIs zerados (causa identificada)
#
#    Investigação cirúrgica refutou hipótese inicial de "lag de ingestão Langfuse"
#    (traces estão queryables na API pública desde 11:58:01.452Z, ou seja,
#    todos os 10 chats têm trace em Langfuse com createdAt < 12:00).
#
#    Causa real: misalignment temporal entre 2 fontes paralelas de dados.
#
#    - Counter requests_total (Observatory): timestamp = momento do heartbeat
#      que captura o incremento do agent
#    - Trace.timestamp (Langfuse): timestamp = momento de início do span
#
#    O 10º chat tem:
#    - trace.timestamp = 11:57:52.570Z (durante execução)
#    - counter requests_total incrementado apenas no heartbeat 11:58:56
#      (após retorno HTTP do chat fechar)
#
#    Consequência observável:
#    - Snapshot [11:56:54.876, 11:57:56.434] enriquece com 10 traces
#      (avg=2550ms, p95=4797ms, cost=$0.014165), mas counter ainda em 9
#    - Snapshot [11:57:56.434, 11:58:56.462] vê delta=1 (counter atrasado)
#      mas calculate_kpis recebe 0 traces (trace órfão tem timestamp do
#      período anterior) → zeros persistidos sem audit error
#
#    Diagnóstico: não é regressão, não é bug de ARI-213. É propriedade
#    emergente do design "counters + Langfuse traces como fontes paralelas".
#
#    Impacto operacional:
#    - Métricas agregadas (várias snapshots): distorção mínima
#    - SLO eval sobre snapshot único: pode mostrar zeros falsos
#    - Frequência: raro em produção com tráfego contínuo; comum em
#      smoke com poucos chats e heartbeat de 60s
#
#    Spin-off registrado em Linear como High severity para tratamento
#    arquitetural futuro (janela de tolerância no enrichment OU
#    reconciliar via trace_id em vez de timestamp).
#
#    Hipótese inicial (rejeitada): "lag de ingestão Langfuse" — refutada
#    empiricamente pela API pública mostrar todos os 10 traces queryables
#    em <10s após emissão.
#
